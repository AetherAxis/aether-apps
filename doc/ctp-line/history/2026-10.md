## #21 查报单 200 行之后连接被 RST（2026-10-30 12:41）

### #21 查报单（回 200 行）之后客户端连接被 RST —— **已修（2026-10-30 12:41 部署验证）**

- **现象**：客户端发 `ReqQryOrder`，前置回「账本 6308 条，回 200 行」，连接被对方 RST：
  前置侧 `会话异常: …远程主机强迫关闭了一个现有的连接`，客户端侧 `[ctp-trader] 前置断开 reason=4097`
  → 自动重连 → 重新登录。后果：查报单拿不到结果，还白搭一次重连（把在途动作搅进对账）。
- **根因（实测定案）**：**响应流水号重复**。旧实现把每行记录帧的 80 族流水写成「首行回显请求计数器、其后 +1」，
  于是同一连接里前一个查询（持仓）刚用过的流水号又被报单行重复使用；官方 `thosttraderapi_se` 见到重复的流水
  就停止派发并 RST。
- **怎么复现这些结论（2026-10-30 搭好的工具链）**：macOS 切片未 strip，可直接读符号表。先
  `lipo -thin x86_64` 抽出单架构（Ghidra provider 拒收 universal），然后
  `otool -arch arm64 -tvV -p <mangled_name> <二进制>` 做定点反汇编（秒级，够用），
  或走 REA + Ghidra 出伪代码：
  `GHIDRA_INSTALL_DIR=~/Tools/ghidra_12.1.2_PUBLIC npx -y rea-agents@6.8.0 decompile <thin二进制> --file-offset 0xcfb9c --snapshot ~/Tools/rea-snaps/ctp-mac`。
  **两个坑**：① `--procedure` 传 demangle 名会报 `Unknown Ghidra procedure name`（`CFTDCPackage::ValidPackage(void)`
  也认不出来），要用 `--file-offset`（Mach-O 的 `__TEXT` 是 `vmaddr=0/fileoff=0`，所以 nm 地址即文件偏移）；
  ② Ghidra 全量分析约 240 秒，`--snapshot` 只有在操作成功时才落盘。
- **SDK 里的确切代码（2026-10-30 反汇编 macOS arm64 切片定案）**：`CFTDCSubEndPoint::HandlePackage(CFTDCPackage*)`
  是收到的报文进派发前的最后一道闸门，它做的是**严格自增**校验：

  ```
  w21 = pkg[+0x30]                    ; A 槽（见下「尚未钉死」）
  w8  = SubEndPoint->GetSeq() + 1
  if (w21 != w8) return -1;           ; ≠「上一包 + 1」⇒ 整包丢弃，不进 HandleResponse
  SubEndPoint->Dispatch(pkg); return 0;
  ```

  **已证实**：
  - `CFTDCProtocol::Pop` 按 `pkg[+0x2a]`（16 位族号）把报文路由到**对应族的** `SubEndPoint`，再尾调
    `HandlePackage` ⇒ 这道校验是**按族**的，不是全局一条。
  - `HandleResponse` 按 `pkg[+0x2c]`（消息 ID，如 `0x6001`）做跳转表分发，**它自己不做任何流水校验**；
    而 `HandlePackage` 在它之前，所以「流水不对 ⇒ 连 `HandleResponse` 都进不去」。
  - 行为上 `HandlePackage` 只返回 0/-1，不直接断连；断连走虚表（`CFTDCSession::Disconnect` 静态找不到
    调用点，只经 vtable 调），触发条件是流水一直对不上把会话判死。
  - 与实测吻合：这正是「重复流水 ⇒ 客户端不派发」那条现象的机制，也是 200 行逐帧 `NextQrySeq` 后
    零断连的原因（每包 +1 连续，全部过闸）。
  - **「按族」这件事有本仓侧的反证**：`CtpFrontSession` 里并存三个独立计数器——`_qrySeqInt`（80 应答）、
    `_rtnInstanceInt`（F0 推送）、`_cmdInstanceInt`（40 指令），它们在同一条连接上交错使用且一直正常。
    如果 SDK 是**全局**一条流水，三个计数器交错早就该被这道闸门全部丢光 ⇒ 只能是按族。
    代码里那句「40 族严格序列——一次自增，OK/ERR 共用（**空跳一格会被客户端拒收**）」是更早的实测结论，
    和反汇编完全对得上。

  **`CFTDCPackage` 对象布局（arm64 反汇编定案，`PreparePackage`/`CreatePackage`/`ValidPackage` 三处互证，
  并由 Ghidra 伪代码独立复核）**：
  对象长 `0x40`，继承 `CFieldSet`。

  | 偏移 | 宽度 | 用途 | 证据 |
  |---|---|---|---|
  | `+0x28` | u8 | 头部字节 0 | `PreparePackage` 写参数；`CreatePackage` 用 `strh 0x4c00` 写 0x28/0x29 |
  | `+0x29` | u8 | 头部字节 1 | 同上 |
  | `+0x2a` | u16 BE | **族号/路由键** | `CFTDCProtocol::Pop` 用它哈希寻址 `SubEndPoint` |
  | `+0x2c` | u32 BE | **消息 ID** | `HandleResponse` 跳转表；`PreparePackage(msgId,…)` 直接写这里 |
  | `+0x30` | u32 BE | **流水序号** | `HandlePackage` 严格 +1 校验；`PreparePackage`/`PrepareResponse` 都显式清零 ⇒ 收发时才赋值 |
  | `+0x34` | u16 BE | 头字段 | `ValidPackage` 反字节序 |
  | `+0x36` | u16 BE | 正文长度 | `MakePackage` 写「写指针−读指针」；`ValidPackage` 用它 `Truncate` |
  | `+0x38` | u32 BE | 头字段 | `ValidPackage` 从缓冲区 +16 取 |

  `ValidPackage` 的做法：`available ≥ 0x14` 否则 -1 → 从读指针**整块拷 16 字节**到 `+0x28` → 对
  `+0x2a/+0x2c/+0x30/+0x34/+0x36` 逐个反字节序、`+0x38` 取缓冲区第 16~19 字节 → `Pop(0x14)`（吃 20 字节头）
  → `Truncate(+0x36)` → 返回 `+0x36 + 0x14`。

  **尚未钉死（别当成结论用）**：`pkg[+0x30]` 对应线上**哪几个字节**还没对上，而且这里有个**算不平**的地方——
  真前置的应答帧（capture 里 446B）在 `02 00 01BA 01 03 34 4C` 之后紧跟着就是 `E1 04 E2 80 01 E3 01 …`。
  若照上表把「从 `01 03 34 4C` 起 20 字节」当作头，则正文长度字段（+0x36）会读成 `0x53E3`，
  和实际 446 字节完全对不上；按任何一种「头在 20 字节处截断」的读法都会把 12 字节正文吃掉，
  而客户端解析持仓/报单字段是正确的 ⇒ **中间还有一层把 `E1/E2/E3` 标记流还原成定宽 20 字节头的转换**。

  这层转换已经找到（不是推测）：接收路径是
  `CFlowReader::GetNext(CPackage*)` → 调 flow 对象虚表槽 `+0x20`（「取一项」解码进调用方缓冲区）
  → `CPackage::Truncate(len)` → `CPackage` 虚表槽 `+0x8`（即 `ValidPackage`）。
  `CNsPackage::ValidPackage` 已确认是**直通**（只 `return 写指针−读指针`），不参与解码；
  解码在 flow 的虚函数里，具体是哪个 flow 子类还没定。

  所以：「我们写的 `NextQrySeq` 槽 == `pkg[+0x30]`」仍是**强推论**（改它就好、改别的没用），不是读码结论。
  要落实得往 `CFlowReader` 背后那个 flow 子类的解码虚函数走，而不是继续读 `CFTDCPackage`。

  **运维要求（按推论）**：本前置在**每条连接、每个族**上写出的流水必须逐包 +1 且连续。任何一次

## #24 交易报单落盘无顺序（2026-10-30 17:47）

### #24 交易所侧的报单落盘是 fire-and-forget，同一行会被"旧值"盖回去（重启后复活僵尸单）—— **已修并部署验证（2026-10-30 17:47）**
- **现象**：交易所内存里早已终结的报单，`sim_order` 表里仍然是 `order_status='3'`（未成交在队）、
  `volume_traded=0`。实测样本：probe1 的 ref `000000000002`——15:29 买入 1 手、**成交了**
  （`sim_trade` 里有 99.37×1、持仓 1 手），但它的报单行从 15:29 起就一直写着「已报入 / 成交 0」。
  2026-10-30 16:05 一次性清 43 笔"僵尸单"时，交易所对每一笔都回 `90009 当前状态「已撤销」不可撤`——
  **内存和库对不上**，而且方向是库更旧。
- **为什么危险**：交易所重启时 `SimOrderManager.Restore` 拿 `sim_order` 当真相源。库里写着 `'3'`
  的单会被当成「上次还没成交的挂单」走作废流程——单子本身不会变成活单（`Restore` 会置成 `'4'`），
  但**库里那行永远是错的**，对账时看起来就像"这笔单一直挂着"。此前 43 笔「僵尸单」就是这么来的：
  查询看得见、内存里早已撤掉、撤单回 90009。
- **根因（读代码定位）**：`SimTradingCore.Persist()` 每次落盘都是 `Task.Run(...)` 火并忘，**没有顺序**：
  ```csharp
  private void Persist(Func<Task> write) { ... Task.Run(async () => { await write(); }) ... }
  ```
  同一行的"插入('3')"和"成交更新('0'/'1')"是两个并发任务，后者先落、前者后落，
  `ON CONFLICT … DO UPDATE` 就把成交结果盖回成插入时的那份旧快照。撤单同理。
- **影响面**：只在重启/对账时才显形，平时无人察觉；一旦显形就是「单子明明撤了/成交了，重启后还在」。
- **怎么修的**：把「并发」改成「串行链」——核心只留一个 `Task _writeTail`，每次 `Persist(write)` 都
  `_writeTail = _writeTail.ContinueWith(write)`；`Flush()` / `FlushAsync()` 等链尾。
  等价于单写者队列，但不需要额外线程/队列，且**落盘顺序 = 内存变更顺序**（不变量）。
  吞吐从"任意并发"降到"单写者"，由 SQLite（WAL 单行 upsert，亚毫秒）决定；本量级（每秒几十单 × 4 条写）
  有余量。`_pendingWrites` 一并删除。
- **钉子**：`aether-exchange/tests/Aether.Exchange.Tests/PersistenceOrderingTests.同一报单的多次落盘必须按内存变更顺序应用`
  ——用一个"被测账户第一笔写必然慢 80ms"的存储把竞态放大成确定性：旧实现下第一笔（插入 `'3'`）会排到
  撤单 `'5'` 之后，断言当场失败（已实测：把 `Persist` 还原成 `Task.Run` 即挂）；串行链下顺序恒定。
  注意过滤必须同时带 `accountId`——maker 的报单号也是 `000000000001`（各账户独立编号）。
- **顺带修掉的第二处（同一类不一致）**：`Restore` 只把非终态报单在**内存**里改成「未成交不在队列」，
  库里那行不动 ⇒ 每次重启都从库里读回 `'3'` 再作废一次，「内存=作废 / 库=已报入」永久分叉。
  现在作废时顺手 `Persist` 一次（同一条串行链），并把 `UpdateTime` 改成这次启动的时刻。
  `PersistenceTests.重启后未成交挂单作废且冻结额清零` 加了直查库断言（`'4'` + `VolumeTotal=0` + 含「作废」）。
- **端到端验证（2026-10-30 17:38–17:47，真实链路）**：
  1. 部署新代码后用 console 报 3 笔（ref `…1301/1302/1303`，价 10/11/12），撤掉 → 库里三行 `order_status=53('5')`、
     `status_msg=已撤销`；
  2. `Restart-Service AetherCtpExchange` 重启 → 再查：**仍是 `'5'`**（旧代码这里会被成 '3' 或走作废）；
  3. 旧代码留下的 53 行 `'3'`（含样本 `000000000002`）在这次启动被作废并落盘，库里 probe1 已无 `'3'`；
     重启后 `订单簿=空`、`未成交=0`，不再有"复活僵尸单"。
- **注意**：`Restore` 不会让 `'3'` 复活成活单——它把非终态单**作废**（`'4'`）并释放冻结，
  所以 #24 的真实危害是「库里永久留着错的状态、误导对账」，而不是"复活"；这一点在验证中得到确认。

## #23 会话跑到第 127 单就不再进单（2026-10-30 16:47）

### #23 会话跑到第 127 单就不再进单（"跑一阵就不干活了，重连又好了"）—— **已修（2026-10-30 16:47 部署验证）**
- **现象（用户可见）**：一条**刚登录、完全正常**的会话，跑到一百二十几单之后开始"空转"——

- **量级（两场实测）**：一场 200 笔报单只落地 **128** 笔（ref 3..128），一场 300 笔只落地 **126** 笔
  （ref 129..254），其余全部静默消失。两场都停在同一个地方，**与推送条数无关**。
- **定位路径**：把前置日志里该会话的每一帧请求拉出来逐条编号，和交易所 `sim_order` 表对账——
  1. 第 127 单起，卖单帧不再被识别：`未知业务帧: body前缀=E101E240 E301E2 E101017B …`；
  2. 同一时刻的撤单帧仍然正常识别（`body[4]==0x06` 位置稳定），所以有应答，只是 90008；
  3. 把 op 字段单独抽出来看，它是一条**逐请求自增的计数器**（买落偶数、撤落奇数）：
     `E4 04`、`E4 06` … `E4 FE`（≤254），越过 255 之后变成 `E3 01 02`(=258)、`E3 01 8E`(=398)…
- **根因（三层，全部在请求侧的收帧识别上）**：
  1. **签名钉死 5 字节**：`MatchesSignature(body,"E101E240E4")` 把 op 字段当成常量 `E4`。实例号一过
     255，SDK 改写成 `E3 <2B>`，整类报单帧从此不再匹配 ⇒ 每张单都掉进「未知业务帧」。
     每笔单消耗 2 个实例号（买 1 + 撤 1），126 笔正好把计数器推到 255——这就是"第 127 单"的来历。
  2. **量字段被锚到帧头**：`FindRunIndex(body, VolShape)` 从帧首扫。`E3 01 32`／`E3 01 34` 整段满足
     VolShape（`0x01 < 0x20` + 尾字节恰好是 ASCII `'2'`/`'4'`），于是"量"锚到了帧头、价格锚空 ⇒
     `ParseOrderInsert` 返回 null。实例号每笔 +2，低字节命中 `'2'`/`'4'` 的恰是 306/308/562/564——
     实测丢的正是 ref 406/407/534/535。
  3. **实例号是 0x0100 整数倍时帧头少一个字节**：256/512 这类值，SDK 写成 `E3 01 E2`／`E3 02 E2`，
     连帧内的 `E1 01 01 7B` 都退化成 `01 01 7B`（少那个 `E1`）⇒ 按 4 字节锚点仍会漏。
     实测丢的正是 ref 681(256)/809(512)。
- **改法**（全在 `CtpOrderWireCodec`，不动协议）：
  - 新增 `IsOrderInsert(body)`：路由 `E1 01 E2 40` + `body[4] ∈ {E4, E3}` + 帧内含 **3 字节尾** `01 01 7B`。
    撤单（`06`）与结算确认（`13`）在这一步被排除，不引入新的假设。
  - `ParseOrderInsert`：量/价格的扫描起点改成 `01 01 7B` 之后（越过整个请求头）；reqId 针尾同步改成 3 字节。
  - 回归用例 `OrderInsertHeaderWidthTests`（9 例，全部用线上实抓帧，含 254/258/306/308/256 五个形态）。
- **修复后实测（probe1 真单，单会话 300 笔买+300 笔撤）**：

  | | 修复前 | 修复后 |
  |---|---|---|
  | 落地报单 | 126 / 300 | **300 / 300** |
  | 会话内推送 | 252（然后静默） | **900**，无一丢失 |
  | 撤单 90008 | 74 | **0** |
  | 实例号跨过 255 / 512 | 卡死 | 正常 |

  900 条推送意味着推送序号也早已越过 251——见 #2 的补注。

   「每隔一轮被堵住的管线吞掉」；
2. 解码：`E1 04 E2 80` 是查报单路由头，之后 **`E3 0x2645`=9797** 是 SDK 的链路计数——它**已经不是**旧签名认的
   `<E4><1B>`，而是加宽后的 `<E3><2B>`（前置日志另有 `E3 0x0340`=832 的早期样本）；
3. 查客户端内核注释：`CtpTrader.QueryRequestCount` 明写「SDK 链路计数第 256 个同族请求起换编码形态」，
   当年的处理意向是「宿主逼近边界前主动重连清零」——**全仓无人实现**（`QueryRequestCount` 只有定义没有消费者）；
4. 进程内复现：同一会话连打 300 次查报单，**第 256 次精确失配**（见下方钉子），日志与线上同形。

**根因**：前置把查报单请求的签名钉死成 5 字节 `E104E280E4`，而 SDK 在链路计数 ≤254 时写
`E4 <1B>`、**≥255 改写成 `E3 <2B>`**（与⑲报单 #23 同一套变宽；计数恰为 0x0100 倍数时，
reqId 标记前的 `E1` 还会被 SDK 吃掉，`E1 01 E1 CD E3` → `01 E1 CD E3`）。越界后整类请求掉进
「未知业务帧」分支→**永不应答**。而查报单是「必须应答」的一族：不应答 ⇒ SDK 查询管线堵死 30s
⇒ 其后所有查询排队/`rc=-2` ⇒ 管线最终被 SDK 自己判死、RST 重连（客户端 4097，前置无辜）。

**改法**（前置侧，宽度无关判据）：

- `CtpOrderWireCodec.IsQueryOrderRequest`：路由头 `E1 04 E2 80` + op 标签 ∈ {`E4`,`E3`,`E2`}（1B/2B/3B）
  + reqId 标记的**尾 4 字节** `01 E1 CD E3`（不吃前导 `E1`，兼容 0x0100 倍数被吃的情形）。
  `E2` 是「宽度+1 ⇒ 标签-1」的外推，为计数 ≥65536（约 2-3 天后）先兜住，尚无实抓样本。
- 同族其它查询（02 成交/04 持仓/06 资金/2A 交易所/2E 合约/3C 结算单）第 5 字节是固定类型码
  （全 <0xE0），与 op 标签不撞——不需要动。
- `CtpTrader` 注释同步改写：那套「主动重连规避」从未实现，正解在前置识别层。

**钉子**：

- `QueryOrderHeaderWidthTests`（12 条）：窄/宽/0x0100 吃掉 E1 三种正例 + 同族六种查询负例 +
  旧判据失配的因果钉；
- `CtpFrontE2eOrderQueryTests.查报单_同会话连打300次_跨过计数255仍每次应答`——**裁判是 SDK 本身**：
  修前第 256 次必挂（已实测），修后 300/300；
- 前置套件 **159/159** 全绿（原 145 + 新增 14）。

**落点**：`ctp-net-front/src/Ctp.Net.Front/CtpOrderWireCodec.cs`（IsQueryOrderRequest + OpTag3B）、
`CtpFrontSession.cs`（查报单分支换判据、reqId 提取改尾 4 字节锚）、
`ctp-net-core/.../CtpTrader.cs`（注释纠偏，代码无改动）。

## #32 「每 30 秒无故断一次」：RPC 一个请求超时就拆整条链路，服务形态下还完全没有 RPC 日志（2026-10-31 12:21 部署）

### 现象

12:00–12:13 前置日志稳定复现，每 ~30 秒一组：

```
会话关闭：交易所连接断开 → 会话异常 90013 → 会话结束: 127.0.0.1:55299 → 会话启动: 127.0.0.1:55377 …
```

每分钟会话启动 3–6 次（12:00 那一分钟 19 次），随部署一起消失过一次又重新出现。
按端口追踪：**botnoise 的连接每次换新**（55496/55498 是 12:06:01/02 刚起的），
**botmm 从 11:51 起一条连接没断过**——所以抖的只有 botnoise 那一侧。

两个反直觉的点：

1. bot 自己的日志里 `已登录` 只有 1 次、`[ctp-client]` 一条重连记录都没有 ⇒ 这轮重连走的是 **SDK 内部重连**，
   根本不经过 `CtpSessionService.ReconnectAsync`。**#30 那个重连退避对这条路径完全无效**。
2. 断开的方向不是客户端：前置是 `CtpFrontSession.OnExchangeLost → Kick("交易所连接断开")`，
   即**前置→交易所的 RPC 链路**被拆掉，前置按设计把对应客户端会话踢了。

### 定位

`SimRpcClient.CallCoreAsync` 的超时分支原来是：

```csharp
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    // 内部超时：连接状态不可信 ⇒ 销毁连接
    TearDownWithEvent();
    throw new ExchangeBusinessException(SimWireErrors.Timeout, "…连接已重置，请重新登录。");
}
```

即 **一个请求 15s 没应答 = 整条 RPC 连接销毁** = 前置 Kick 客户端会话 = SDK 重连。
掉线周期 ~30s 与「15s 超时 + 重连 + 下一轮超时」吻合。

之所以只能推到这里、拿不到「是哪个 op 慢」：两个 host 都跑成 **Windows 服务**，没有控制台，
而 RPC 层的诊断全部走 `Trace.WriteLine`——**没有监听器**。交易所日志从启动 banner 之后一片空白
（`ctpsim-exchange.log` 的 mtime 一直停在启动那一刻），前置日志只有 `会话关闭：交易所连接断开` 这种结论行。
一句话：现场看得见「断了」，看不见「为什么断」。

### 改法

1. **超时不再拆链路**：单次超时只让该请求失败（迟到应答按 id 查表 miss 天然丢弃）；连续
   `MaxConsecutiveTimeouts=3` 次才判定链路失效并拆除（否则服务端卡在一个长 op 上会把后续调用全部吊死）。
2. **慢应答留痕**：≥3s 记 `[CTP-SIM] 慢应答 Nms：op=…`；超时记 op 名与耗时、连续第几次。
3. **两个 host 都接 Trace → Log.Line 监听器**（`LogTraceListener`）：RPC 诊断与业务日志进同一个文件。
4. 接收循环中断 / 坏帧 / 分发异常都补上异常类型——「链路怎么断的」不再靠猜。
5. `SimRpcClient` 构造增加可选 `requestTimeoutMs`（默认仍是 15s），供测试钉「超时不拆链路」。

### 钉子

`SimRpcTimeoutKeepAliveTests`（裸 TCP 假柜台：hello 正常回、`queryAccount` 前 N 次装死）：

- 单次超时 ⇒ 抛 `90014`、`IsAlive==true`、下一次调用照常成功；
- 连续 3 次超时 ⇒ 抛 `90014`、`IsAlive==false`。

`Aether.Exchange.Tests` 全量 **145/145**。

### 验收

12:21–12:24 三分钟**零掉线、零会话启动**（改前 ~2 次/分钟）。触发点是否彻底消失要靠长跑观察；
真出现慢应答时日志里会有 `[CTP-SIM] 慢应答/请求超时 op=…`，届时就能点名是哪个 op。

- 新增参数 `MinSideLots`（默认 1）：预算 = `max(仓限 − 敞口, MinSideLots)`，触限侧只保留**最外一档保底腿**，
  `RollStaleLegs(capped)` 从「全撤」改成「留保底档、撤其余」。
- 新增参数 `ReduceIntervalMs`（默认 3000）：减仓单重挂节流。
- 新增两处健壮性：`SameLevel` 半 tick 容差（brokerage 会把 117.09375 取整成 117.09，精确相等会让每条腿
  每轮都被判「移出带宽」⇒ 撤挂风暴）、被拒档位 3s 冷却（被拒的票不进腿表，否则下一轮照样重报）。

### 教训

- **「策略以为在挂单」和「交易所真的有单」是两件事**。这一轮的三个坑全在这里：预算算成负数（策略自己
  不挂了）、被拒（策略挂了但没发出去）、被拒（发出去了但交易所不认）。查这类问题必须三段对齐：
  **策略日志 → brokerage 日志 → 交易所/前置日志**，缺一段就会把 A 的病因记到 B 头上（#33 当时就记错过）。
- **Lean 的本地风控在实盘 CTP 上是负资产**：它按自己的模型重复扣保证金，和交易所的算法不一致。
  拒单权应该只有一个主人（交易所），客户端只需把拒单如实回报。
- 孤儿单不只占簿位，**还会把账户的可平量锁死**——这个副作用此前完全没被记录过。

## #30 / #36 / 可平量 —— 「无缘无故断开」的另一半，与做市商被自己的平仓腿锁死（2026-10-31 16:48 部署验证）

### 症状（先看现象，别看结论）

probe1 走前置那条线，一个会话好好跑着，然后**每 1~4 分钟来一次**这样的序列：

```
下单 10s 未收到报单回报，判无效: ax001 BuyClose 1手 ref=000000003150
持仓查询失败（沿用缓存快照）: 持仓查询 5s 未返回（会话半死？重连窗口内调用挂起）
对账跳过：查报单失败（对账查报单 8s 未返回（会话半死？重连窗口内调用挂起））
对账跳过：查报单失败（One or more errors occurred. (ReqQryOrder 发送失败 rc=-1)）
[ctp-trader] 前置断开 reason=4097
```

前置侧同一秒钟的日志是：

```
会话异常: Unable to read data from the transport connection: 远程主机强迫关闭了一个现有的连接。
会话结束: 116.232.137.131:51406
```

关键词：**前置没踢人**（没有 `同账户新会话登录`），是客户端 OS 发了 RST。但客户端为什么要发 RST？
因为它在这之前**已经有十几秒收不到任何应答**了——`rc=-1`（未就绪）/`rc=-2`（未处理请求超许可）
都不是网络错误，是 API 自己在本地拒发。会话「半死」在前，RST 在后。

### 根因一：客户端把查询发叠了（`ctp-net-core`）

真 CTP 交易 API 的查询是**全局串行**的，这条约束由 API 自己执行：上一笔查询还没应答就再发一笔 ⇒
`rc=-2`；1 秒内发第二笔 ⇒ `rc=-3`。而客户端从没设过闸，两条路径各在各的任务里跑：

- `CtpBrokerage.RefreshPositionCacheIfStale()`：**每次报单前**刷新持仓，2 秒节流；
- `ReconcileWithExchange()`：每 20 秒查一次报单（200 行 ≈ 89KB、几十帧）。

两笔撞上就是 `ReqQryInvestorPosition 发送失败 rc=-2`。更隐蔽的一半是**多帧应答被穿插**：查报单的
几十帧还在流，另一笔查询的应答插进来，API 的请求-应答通道错序——它不报错，直接强拆 TCP。
这也解释了为什么「只查报单、不跑做市商」的会话从来不断：没有第二条并发查询。

**修**：`CtpTrader.RunQueryAsync` —— 8 个 `Query*Async` 全部改走同一把闸（`SemaphoreSlim(1,1)`），
且两笔之间至少隔 1 秒（CTP 的 1 秒/笔流控）。下单/撤单不过闸（CTP 里是另一套更大的额度）。

### 根因二：前置在写 TCP 的线程上逐帧同步写盘（`ctp-net-front`）

```csharp
await foreach (var frame in _out.Reader.ReadAllAsync(ct))
{
    _log($"[CTP-Front] → [{frame.Length}B] {Convert.ToHexString(frame)}");  // ← 每一帧
    await stream.WriteAsync(frame, ct);
}
```

`_log` 是宿主的 `Console.WriteLine` 重定向到文件、逐行 flush。做市商每秒几十帧 ⇒ 每秒几十次
「十六进制格式化 + 同步写盘」压在**唯一写 TCP 的线程**上。磁盘一有抖动，写循环跟着卡，所有应答
（报单回报、查询应答、心跳应答）排队发不出去 —— 这就是上面那十几秒「半死」。一天 443MB 的
`ctpsim-front.log` 只是副产品，真正的代价是它把会话拖死了。

**修**：`FrontFrameTrace.Enabled`（`AETHER_CTP_FRAME_TRACE=1` 才开，默认关）。出站帧、入站帧、
行情 tick 推送行、报单/撤单的 body 十六进制全部进开关；**语义日志（会话/登录/报单/撤单/拒单）
始终记录**，排障不受影响。

### 附带：做市商被自己的平仓腿锁死（映射器可平量扣减）

90006 一直清不干净（实测 2.5 分钟 13 次）。交易所按**在挂平仓腿的剩余量**预留可平量
（`SimTradingCore.ReservedCloseVolume`），而映射器只看 `|净仓|`：净空 24 手时每档买腿都映射成
`BuyClose`，第一张就把 24 手里的 1 手占住，后面的腿全部 `[90006] 无可平持仓`。

**修**：`CtpOrderRequestMapper` 入参加 `RestingCloseVolume`（brokerage 从 `_tracker.LiveChildren`
现算），可平量 = `|净仓| − 在挂平仓手数`；扣到 0 就把这条腿**改开仓**——净空下买入本来就是在减敞口，
交易所不预留、不拒单。真做市商也是这么干的。三个单测钉住（够平 / 扣光改开 / 超量拆平+开）。

### 验收（2026-10-31 16:37–16:48，11 分钟，probe1 走前置）

| 指标 | 修复前（同环境） | 修复后 |
|---|---|---|
| `前置断开 reason=4097` | ~1 次 / 2.5 分钟 | **0** |
| 重新登录 | 每次断开一次 | **0** |
| `[90006] 无可平持仓` | 13 次 / 2.5 分钟 | **0** |
| `持仓查询失败` / `ReqQry* 发送失败` | 6~7 次 / 2.5 分钟 | **0** |
| 腿表 | `在挂 买36~44`（僵尸占位） | **买3/卖1~3**（正好 3 档） |
| 前置日志体积 | ~24MB/小时 | **110KB/小时**（≈200×，只留语义行） |

### 教训

- **「断开」是最后一步，不是第一步**。先去客户端日志里找**断开之前**有没有「没应答」的请求，
  再看前置有没有主动踢人；只看 `reason=4097` 会一直在网络层打转。
- **诊断代码放错位置会变成故障源**。同一行 hex 日志，放在空闲线程里是证据，放在唯一写 TCP 的
  线程里就是单点故障。任何「每帧都做」的事情都要能一键关掉。
- **合规不是可选项**：CTP 的「查询 1 秒/笔、全局串行」是 API 强制的，客户端省掉这道闸，
  换来的不是速度，是偶发的整条链路被拆。
- 僵尸腿（#36）是根因的下游产物：会话半死时下的单既收不到回报也撤不掉。根因修掉后它不再新增，
  但**存量只能靠重启清**——腿表该有自己的存活看门狗。
