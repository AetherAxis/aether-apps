# 为什么「起两个 bot、让行情动起来」不是一个简单需求

> 面向：想快速验证仿真市场的人。
> 结论先行：**这条链上没有一个环节是「打开就有」的**——它是四个进程（交易所 / 前置 / 两个 bot）＋一套逆向出来的二进制协议 + 三个各自独立的硬限制叠在一起的结果。任何一个环节错位，表现都是同一句话：「行情不动」。
> 相关缺陷细节见 `../../ctp-net-client/doc/session-reauth-after-reconnect.md`；装配与边界见 `../DESIGN.md`。
> 2026-10-29 之后的临时形态（bot 直连交易所、绕开前置）见 `direct-bot-bypass.md`；行情投递契约见 `../../ctp-net-front/doc/md-tick-delivery.md`；客户端同值去重的判定与移除见 `../../ctp-net-core/doc/md-tick-dedup.md`。

## 1. 需求的真实形态

用户原话：「启动两个 bot，让行情能模拟真实行情动起来。」

拆开看，它实际要求同时成立：

| # | 隐含前提 | 谁来满足 |
|---|---|---|
| 1 | 交易所进程在撮合，且能收到报单 | `Aether.Exchange.Host` :17800 |
| 2 | 前置在正确翻译 CTP 二进制协议 | `Aether.CtpFront.Host` :17801/:17802 |
| 3 | 两个 bot 都是**已认证、已登录**的会话 | `ctp-net-client` 会话状态机 |
| 4 | 做市商挂出阶梯，噪声单吃掉它 | `algorithms/*.lean.cs` |
| 5 | 成交 → 交易所产生 tick → 前置推给订阅者 | 事件链，不是配置 |
| 6 | tick 的价格分布**看起来像真行情**，不是两个点来回跳 | 策略参数 |

缺 1~5 任何一环，桌面端只是「连上了但一片死水」；缺 6 则是「动了，但一眼假」。

## 2. 困难点清单

### 2.1 协议是从抓包逆向出来的，且对字节宽度零容忍

前置侧没有官方协议文档，帧结构靠抓包还原。这不是「能跑就行」的松耦合：**帧宽度必须逐字节精确**。

- 变形即灾难，实测过两次：把一个 183B / 4 记录的订阅应答裁成 2 记录 → native 侧把同一帧反复重投，**15 秒 903,483 条回执**，进程直接被打死；
- 合约槽是 6B 定宽、填充字节是 `EF`（该编码的「空」）而不是空格，超长按槽截断；
- 少写一条记录也不行：native 解析器按槽内字符串长度逐条走，5 字符合约名会让它只走 3 条记录。

所以这类改动不能凭「看着对」上线，必须跑完整帧断言（`ctp-net-front` 现在 95 例）。

### 2.2 回报推送的 F0 序号有 1~251 硬上限

官方 SDK 只接受该区间内的序号，服务端无法扩域（2026-10-19 实证）。前置的应对是**累计到 240 条就主动断开客户端**，靠 SDK 自动重连把序号归零（`ctp-net-front/src/Ctp.Net.Front/CtpFrontSession.cs:198`，`:306-312` 执行 `Close`）。

活跃行情下 240 条几秒就攒满 —— 事故现场一秒内连断 12 次。这是**设计**，不是 bug，但它的代价是：**连接在业务高峰会被反复掐断**。

### 2.3 认证状态是 per-connection 的，断了就得重认证

CTP 的 `ReqAuthenticate` / `ReqUserLogin` 绑定在当前 TCP 连接上。前置主动断开后，SDK 自动重连开出的是新连接，认证状态归零。

而客户端只在「首次登录」时发认证帧 —— 重连后若没有重新认证，**所有报单会被前置当垃圾帧丢弃**，且客户端侧状态仍显示「已连接」。本次事故丢了 117 张报单，市场因此静默停摆。详见 `../../ctp-net-client/doc/session-reauth-after-reconnect.md`（未修复）。

这是最反直觉的一条：**「登录成功过」不等于「现在这条连接已认证」**。

### 2.4 行情不是「行情源」，而是成交的事件产物

仿真市场没有外部行情源。tick 完全由订单簿变动／成交驱动：

```
bot 报单 → 交易所撮合 → 成交或簿变更 → 交易所推 tick → 前置转发 → 客户端
```

所以「没有 tick」的第一嫌疑永远是**上游没有成交**，而不是行情服务坏了。本次排查里，「行情死了」的真实含义是：做市商报告没送进去 → 阶梯撤空 → 存量单被吃完 → 没有新成交 → 没有新 tick。因果链是反的。

### 2.5 「动起来」和「像真实行情那样动」是两件事

即使链路全绿，价格分布仍由策略参数决定。实测（两个 bot 跑 5 分钟，远程前置）：**494 条 tick、979 笔成交，但 `LAST_DISTINCT=2`（98.62 / 98.64）**。

原因：做市商以 `last` 为锚，`RepriceThresholdTicks=2`，噪声 bot 每次都在吃同一档内盘报价 —— 价格被锁在一个两跳带宽里。这是**参数**问题，不是链路问题。可调的旋钮：

- 噪声 bot 的报价锚点随机化（现在固定吃同一档）；
- 下调做市商 `RepriceThresholdTicks`；
- 增大噪声单的尺寸/对手档位跨度。

要在桌面端看起来「像真行情」，必须调这几个参数 —— 而它们分散在两个 `.lean.cs` 里，且改完要重新走部署覆盖。

> **2026-10-29 重置 venue 后的实测**（结论：已经不是两跳了）：桌面端连远程前置采样 2 分 14 秒，
> 110 条 tick 里 `last` 走过 99.9531–100.0469（6 个价位），累计量 2369→2456（+87 手）。
> 真正把价格锁死的不是参数，而是当时**盘口只剩买盘**（撤单断连丢失 ⇒ 54,738 张僵尸买单），
> 处置见 `direct-bot-bypass.md` §6。

### 2.6 撤改挂单会自激（tick ⇄ 报价回路）

做市商每收一笔 tick 就维护一次阶梯，而撤改挂单本身又是一次簿变更 ⇒ 新 tick。不节流时这个回路在同一毫秒内自我放大：实测把前端灌到每秒几百帧同值快照，客户端 native 侧积压后表现成「同一笔 tick 反复重投」，**bot 日志 30 秒涨到 160MB**。

已修：`MinQuoteIntervalMs`（默认 300ms）只丢中间态，下一次允许的报价始终用最新价；30s 兜底定时器以 `force` 绕过节流（`algorithms/readme.md`）。

> 2026-10-29 复核补充：当时为了压住这条回路，客户端还加过一层「同值 tick 去重」（不看时间戳，只比 8 个量价字段）。
> 实测**重复并不是从这条路来的**——逐字节相同的帧已由前置挡掉，客户端 0 次收到；那层去重反而把
> 「内容相同、时间前进」的合法快照当重复丢掉（11/382）。该层已移除，见 `../../ctp-net-core/doc/md-tick-dedup.md`。

### 2.7 日志两难：治好了磁盘，也关掉了证据

同一轮里两个相反的需求撞在一起：

- 不节流 + 全量日志 ⇒ **单 bot 8.6 GB/天**，服务器磁盘被撑爆；
- 于是生产 bot 的 stdout 改成 `>NUL` ⇒ 客户端侧**零可观测性**。

结果：2.3 那个事故只能靠前置日志反推，无法确认 SDK 到底有没有回调 `FrontDisconnected`。正解是「极简会话日志」（只记 连接/认证/登录/断开/重连，按天轮转 + 单文件上限），代价几十 KB/天 —— 已列入待办，尚未实施。

### 2.8 双 bot 必须两个账户、两个实例目录

`DESIGN.md` 3.2「一个目录一个实例」：`config.json` / `labs` / `ctp.db` 全按 cwd 解析。两个 bot 必须是**两个账户**（同账户 `OrderRef` 撞号，报单互相覆盖），且各自一套实例目录。部署时 `publish/` 整替换、实例 `config` 永不覆盖。

### 2.9 改一行源码要过一整套部署链

所有跨仓接线都是 `ProjectReference` 相对路径，因此：

```
改源码 → 停 bot 进程（否则 exe 被占用）→ deploy-from-local.sh 发布 → 覆盖 exe → 重启计划任务
```

中间有几十秒的撮合中断。且桌面端/客户端**很容易连错前置**——本次排查里就出现过一次「以为在验证远程前置，实际连的是 SimNow」，用 PX612/SH701/IF2612 这些真实品种的价格证明的（远程前置只会回 `ax001`）。

## 3. 一分钟自检清单

行情不动时按顺序打：

```powershell
# 0) 端口在听吗（17800 交易所 / 17801 交易前置 / 17802 行情前置 / 17805 账本）
Get-NetTCPConnection -State Listen -LocalPort 17800,17801,17802,17805 | Select LocalPort,LocalAddress

# 1) 两个 bot 进程在吗（2026-10-29 起跑的是直连家族 Aether.DirectBot.Console；CTP 家族是 Aether.CtpConsole）
Get-Process | Where-Object { $_.ProcessName -like 'Aether.*Console' } | Select ProcessName,Id,StartTime

# 2) 前置最近有没有在推 tick（日志行自带墙钟时间戳；日志是 UTF-8，必须 -Encoding UTF8）
#    每条推送长这样：2026-10-29 17:24:04 [CTP-Front-MD] → 推送 tick: ax001 last=… bid=… ask=…（去重跳过 N）
Get-Content 'C:\Aether\ctpsim-data\ctpsim-front.log' -Tail 400 -Encoding UTF8 |
  Select-String -SimpleMatch 'tick: ' | Select-Object -Last 3

# 3) 有没有「240 上限」+ 之后的「等认证」（= 命中 2.3 缺陷）
$t = Get-Content 'C:\Aether\ctpsim-data\ctpsim-front.log' -Tail 80000 -Encoding UTF8
($t | Select-String -SimpleMatch '240 上限').Count
($t | Select-String -SimpleMatch '认证: broker').Count
($t | Select-String -SimpleMatch '等认证').Count      # 期望 0
```

判读：

| 现象 | 结论 |
|---|---|
| 端口缺 | 交易所/前置没起 |
| 端口齐、进程在、前置日志 60 秒内无 `推送 tick` 行 | 大概率 2.3（重连未重认证）或 2.4（没有成交） |
| `等认证` > 0 | 命中 2.3 缺陷 —— **重启 bot 进程可临时恢复**，根因未修 |
| 有 tick 但 `LAST_DISTINCT=2` | 链路正常，属 2.5 参数问题 |

## 5. 一句话回答「为啥办不到」

因为「行情动」不是某个开关的输出，而是**一条事件链的末端**：认证要挂在当前连接上、帧要逐字节精确、序号上限会周期性掐断连接、tick 只能由成交产生。链上任意一环断了，末端表现完全一样 —— 所以每一步都必须能被观测和断言，而这恰恰是本轮花掉最多时间的地方（日志被关掉之后，只能靠前置侧日志反推）。
